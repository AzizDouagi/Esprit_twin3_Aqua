2. Diagramme du processus DevOps

PhaseCe qui est fait dans AquaSecure
1. PlanifierBesoins traduits en phases et critères d'acceptation, issues GitHub (modèles bug et fonctionnalité).
2. CoderUne branche par phase (feature/*, devops/*), commits au format Conventional Commits, tests écrits avec le code.
3. Construirecomposer install, npm run build (Vite), images Docker app (PHP-FPM, non-root) et web (Nginx).
4. TesterLaravel Pint, PHPStan/Larastan, PHPUnit (111 tests), composer audit, npm audit.
5. LivrerMerge --no-ff sur main, tag sémantique vX.Y.Z, images publiées sur GHCR avec les tags sha, semver et latest.
6. DéployerStaging puis production par SSH, avec la même image ; la production exige l'approbation de l'environnement GitHub.
7. ExploiterCompose : MySQL, application, Nginx, worker de file d'attente, scheduler Laravel, Mailpit.
8. SuperviserHealthchecks /up et /health, logs applicatifs, journal ai_logs ; les retours alimentent la planification.

3. Pipeline : développement, CI, CD

3.1 Intégration continue (ci.yml)

Déclenchée sur chaque pull request, sur les push des branches feature/**, devops/**, docs/**, et appelée par la CD (workflow_call). Permissions minimales : contents: read.

JobÉtapes
quality (matrice PHP 8.2 et 8.3, service MySQL 8.4)composer validate --strict · composer install · migrate:fresh --seed · composer lint (Pint) · composer analyse (PHPStan) · php artisan test avec couverture clover/JUnit exportée en artefact · npm ci et npm run build · composer audit et npm audit · validation YAML, scripts shell et docker compose config
imagesBuild des cibles app et web · docker compose up --wait sur une base isolée · curl sur /up et /health · nettoyage des conteneurs

3.2 Livraison et déploiement continus (cd.yml, deploy.yml)

ÉtapeConditionAction
cipush sur main ou tag v*Réutilise ci.yml ; rien n'est publié si la CI échoue.
publishaprès ciBuild et push de deux images vers ghcr.io : tags sha-…, semver et latest (sur tag).
stagingvars.DEPLOY_ENABLED == 'true'Déploiement SSH : sauvegarde, migrations, up, smoke tests.
productiontag v*, après staging, approbation de l'environnementMême image que staging ; up, /health, smoke tests.
rollbackéchec de démarrage ou de smokeRetour aux images précédentes ; le schéma de base de données est conservé, la compatibilité reste à vérifier.

Secrets et variables GitHub à créer pour un déploiement réel : SSH_HOST, SSH_USER, SSH_PORT, SSH_PRIVATE_KEY, SSH_KNOWN_HOSTS, vars.DEPLOY_PATH, vars.DEPLOY_ENABLED.

4. Architecture Docker

  • Build multi-stage : compilation Vite, puis images de runtime app (utilisateur non-root, OPcache) et web (Nginx unprivileged).
  • Healthchecks sur chaque service ; docker compose up --wait attend leur état sain.
  • Séparation développement et production : en production, APP_DEBUG=false, aucun phpMyAdmin ni Mailpit, port publié sur 127.0.0.1 uniquement.

6. Limites assumées

  • La CI et la publication GHCR ont été exécutées sur GitHub avec succès pour le commit 13d7ee3 (capture 6).
  • Le déploiement SSH vers staging et production n'est pas activé : il demande un serveur, les secrets SSH et DEPLOY_ENABLED=true. Il est décrit et validé syntaxiquement, mais n'a pas été exécuté.
  • La pile Docker de validation a été lancée localement puis supprimée ; les captures 4 et 5 en sont la trace.
  • Le rollback restaure les images, pas la base de données : toute migration destructive doit être vérifiée avant production.
